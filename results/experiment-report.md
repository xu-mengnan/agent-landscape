## 如何复现

在仓库根目录运行：

```sh
python scripts/run_checks.py
```

需要Python3.10及以上和标准库SQLite。无需安装任何第三方依赖，不读取API密钥，不调用外部API。脚本会更新本目录的结果JSON和日志。当前只在上表所示Linux环境执行过；兼容写法不等于已测过Windows/macOS。

## 已验证的机制

**返回丢失与幂等**：负对照中两次调用产生两次效果；修正版将幂等键和参数摘要写入下游模拟服务，由它原子判重。返回丢失后再次调用仍保留一次效果，本地任务随后完成。

**真实进程终止**：测试通过独立Python子进程运行worker，在下游已提交、上游未记完成的边界调用os._exit(23)。检查下游仍有一次效果、任务仍pending；启动另一子进程恢复后done，效果仍一次。这里没有模拟机器断电或文件系统损坏。

**并发判重**：4个线程发起16次相同下游请求，只有一次新增效果。同一幂等键配不同参数被拒，不允许误把不同业务意图合并。

**状态流转**：两个相同版本写者只有一个成功；旧版本回调被拒；非法阶段跳转和终态回退被拒。此CAS试验使用本地SQLite，不是跨数据中心一致性测试。

**权限与取消**：事后检查能够拒绝但无法抹去先前动作；执行前检查将效果数保持零。取消在派发前被检查；已经完成的动作不能由取消撤销。

**记忆规则**：可信应用赋予的来源、版本、TTL、租户范围和删除墓碑按既定规则生效。实现是内存KV，没有真实检索/压缩/向量索引，不能据此声称实现生产分层记忆。

## 为什么30项都通过不等于完美系统

三项`negative_control`测试的成功代表“预期错误确实发生”。其余测试仅覆盖明确构造的情况。没有调用真实SDK，没有随机LLM任务，也没有吞吐排名。

任务表和下游分别使用两个数据库，刻意展示非原子边界。只有因为模拟接收方支持稳定键去重，重放才不会重复产生效果。若实际接收方不具备此契约，outbox不能单独提供exactly-once；需要查询/对账或人工补偿。

取消发生在权限检查之后、下游提交之前仍可能存在竞态，本实现不会宣称它能回滚外部效果。多worker租约、网络分区、多机故障、恶意输入、限流退避、集群数据库和真实业务补偿均未实现/验证。
