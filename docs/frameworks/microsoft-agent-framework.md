## 工程解释（I）

企业集成能力与业务正确性不是同一个维度。服务身份、现有遥测或开发语言兼容可以降低接入成本；但每条可恢复流程仍需要明确：检查点包含什么、不包含什么，恢复后哪些函数会再次进入，以及外部系统能否识别同一个操作。

节点ID不应随每次部署随机生成。对于升级后恢复旧工作流，应记录工作流版本、节点映射和迁移策略，无法恢复时进入人工处理，而不是从头再做所有写操作。

## 反序列化与存储（I）

检查点后端本身是敏感数据面。限制谁能读写、限制允许类型、校验来源，优于把任意文件当可信恢复快照。即使某个序列化工具有限制，也不应允许用户上传未经审核的检查点并在高权限服务内加载。

## 场景判断（I）

当团队已有适配的语言栈、身份体系与运行设施时，可以将它与显式图运行时一起评估。比较应包括开发者实现状态机、恢复、审批和审计所需的额外代码量，而不只比较模型调用的几行示例。

## 最小验收

同版本重启、同拓扑重建、改节点ID、删除节点、检查点损坏、外部动作返回丢失六个场景分别记录。后两项应允许安全失败或进入人工处理，不要求“无论如何都恢复成功”。
