# 八层分析框架与责任分配

以下分类是本项目的分析工具（I），不是任何厂商的官方固定分层。

## 总体结构

```text
任务目标 / 完成标准 / 用户纠正
                 ↓
任务与流程控制 ── 人工审批 / 取消
                 ↓
Agent循环 / 显式图 / 子任务协调
                 ↓
上下文装配 ← 最近对话 + 权威状态 + 可检索记忆 + 证据
                 ↓
工具与技能选择 → 参数校验 → 执行点授权 → 幂等业务服务
                 ↓
环境真实结果 / 产物 / 业务状态

横切：事件日志、检查点、Trace、预算、租户边界、版本与保留策略
```

## 八层需要逐项回答的问题

|层次|核心责任|验收问题|
|---|---|---|
|任务交互|澄清目标、完成标准、纠正/取消|用户改需求后旧计划是否失效？|
|决策编排|循环、图、路由、子Agent|哪些由模型决定，哪些必须固定？|
|工具/Skills|发现、加载、Schema、权限|工具名字正确是否仍可能越权？|
|上下文|检索、摘要、裁剪、引用|被压缩的是噪声还是关键限制？|
|记忆/业务状态|事实、版本、来源、过期、删除|谁能改变支付状态或用户偏好？|
|持久执行|进度、重试、恢复、任务调度|故障发生在哪个提交边界？|
|环境与产物|文件、沙箱、进程、浏览器|恢复会话后工作目录是否还在？|
|观测与评估|过程关联、终态校验、成本|成功是否由独立检查而非自报决定？|

## 不同“状态”不能混装

**对话历史**记录说过什么；**工作流检查点**记录执行到哪里；**业务状态**记录事实是否成立；**运行环境**保存文件和进程相关资源；**审计事件**说明发生过什么。五者有不同寿命、权限和恢复策略。

例：用户说“已经支付”属于输入事实声明；查询交易系统得到“未支付”属于权威业务观察；模型摘要不能把前者覆盖后者。用户说“不要再联系”则是偏好/授权约束，不能因交易系统没有该字段就被丢掉。来源优先级必须按字段定义，不能一个全局置信度解决所有冲突。

## 恢复是一组契约

1. 接受任务前或之后如何持久化任务意图？
2. 模型输出和工具参数是否记录，以及记录的是完整输出还是未完成流？
3. 接收方是否已产生业务效果？
4. 返回结果丢失后如何对账？
5. 哪些步骤允许重放，哪些只能查询状态或人工补偿？

LangGraph文档区分checkpointer/store，Microsoft文档强调恢复拓扑与标识，DeepSeek文档区分持久和运行时事件。[S07][S15][S17] 这些事实共同提示要逐层检查，而非仅确认一个resume按钮。

## 多Agent应该被证明有价值

建议保留单Agent+相同工具作为基线。仅当任务可分解、上下文确实需要隔离、结果可合并时引入子Agent。父任务必须定义预算、超时、取消传播、子结果格式、冲突仲裁和失败收敛。并行数量应是可调资源限制，不是架构先进程度。

## Trace不是审计数据库

面向调试的Trace可以有采样、批量导出和敏感数据配置；业务写入审计需要更强的身份、完整性和关联要求。即使框架自动生成Trace，也要检验实际导出目的地和丢失窗口。[S04] 不应把包含用户全文的观测默认配置直接用于生产或公开研究。
