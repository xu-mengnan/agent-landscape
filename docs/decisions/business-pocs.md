# 三个业务验证设计：先隔离验证，再灰度接入

以下完全为通用设计与合成用例，不描述任何公司的内部实现或数据规模。

## A. 多轮对话的上下文与记忆

目标：比较完整历史、滑动窗口+摘要、结构化记忆+检索。固定模型、原始对话和检索素材，避免不同数据质量污染对照。

数据模型建议：`tenant_id / subject_id / key / value / source / evidence_ref / revision / observed_at / expires_at / deleted`。业务事实由权威工具确认；偏好由用户更正；摘要记录来源，不能直接写权威业务字段。

流程：对话事件落库→提取候选事实→按字段验证→CAS更新→更新检索索引；生成时读取有效状态与最近窗口。删除要求还应传播至摘要、向量索引、缓存及允许清理的副本；本包Memory实验仅覆盖内存KV，不证明完整删除链已经实现。

指标：最新约束保留率、错误覆盖数、证据可追溯性、Token与时延；删除/跨租户问题作为门槛。回滚：关闭记忆写入和新检索路由，保留原对话来源，不静默覆盖历史。

## B. 轮次后置建议与阶段推进

目标：生成候选建议不阻塞主对话，且不使用过时快照更新状态。

建议事件字段：`tenant_id / user_id / conversation_id / turn_id / state_version / event_id`。消费者接收事件后核验当前轮次与版本，再生成候选；写回前再次校验版本和合法阶段，已进入下一轮的结果应丢弃或降为草稿。

流程：对话完成→持久事件/队列→去重→读取状态快照→生成→业务规则校验→CAS落库或拒绝→审计。模型不直接做无条件UPDATE。

验证：重复消息、乱序消费、旧回调、校验失败、模型超时、任务取消。验收不只看“生成成功”，还要看结果是否被正确采用或拒绝。回滚：新生成走影子模式，不改变业务状态，保留原链路。

## C. 异步批处理与通知

目标：在预算和时间窗内执行候选任务，并避免重复发送、失效授权或状态变化后错误触达。

流程：候选生成→持久任务表→分片/队列→限流worker→发送前重查偏好与状态→授权→接收方幂等API→结果回写/对账。幂等键由稳定业务意图构造；同键不同参数拒绝。

将基础设施吞吐与真实模型质量分开：模拟模型可测调度压力，但不能据此报告真实模型链路容量。错误分类区分可重试、永久失败、状态已变化和结果不确定。重试耗尽进入对账，而不谎报未发送。

验收：重复效果数、授权违规、过期任务发送数、对账覆盖、预算使用和人工处理。回滚：暂停消费与发送开关；已经发送不能由“取消”撤销，需要单独补偿策略。

## 共同实施顺序

先选择一个可量化问题，不同时改造三条链路。建立旧方案基线；用合成数据验证；脱敏影子流量；小范围灰度；满足门槛才扩大。所有数值阈值应由业务风险和SLO确定，本报告没有编造实际改善百分比。
